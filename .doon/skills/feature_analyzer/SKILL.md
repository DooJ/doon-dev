# 기능 분석기

- Android 프로젝트에서 계층 경계나 아키텍처 해석이 중요할 때만 `../android_architecture/SKILL.md`를 불러옵니다. 다른 플랫폼은 해당 저장소의 아키텍처와 규칙을 기준으로 판단합니다.
- 동작을 설명하기 전에는 반드시 소스 코드를 읽습니다. 코드가 지원하지 않는 기능을 추정해서 쓰지 않습니다.
- 기능 의도가 여러 방식으로 해석될 수 있으면 가능한 해석과 확인 근거를 나눠 적고, 확인되지 않은 의도를 하나로 단정하지 않습니다.
- 특정 기능을 분석하는지, 프로젝트 전체를 역기획하는지 먼저 구분합니다. 애매하면 `references/analysis_scope_router.md`를 읽습니다.
- 분석 결과를 상시 문서로 승격해야 하거나 사용자가 문서화를 요청하면 `references/reverse_engineering_living_doc_bridge.md`를 읽고 `living-doc-writer`로 넘길 근거와 대상 문서를 정합니다.

## 프리앰블

- 분석 범위가 `기능 역기획`, `프로젝트 전체 역기획`, `온보딩 구조 분석`, `문서화용 명세 추출` 중 무엇인지 먼저 확정합니다.
- 기능 역기획이면 대상이 `모듈`, `화면`, `API`, `배치/워커`, `엔드투엔드 플로우` 중 무엇인지 확정합니다.
- 프로젝트 전체 역기획이면 도메인 목록, 진입점, 화면/API, 데이터, 아키텍처, 운영/테스트/문서 갭을 함께 훑습니다.
- 사용자가 원하는 산출물이 개요인지, 상세 흐름인지, 리빙독 갱신용 근거인지 먼저 확인합니다.
- 범위를 확정하기 어렵다면 먼저 관련 파일 후보, 진입점 후보, 추정되는 플로우를 짧게 정리한 뒤 확인 가능한 범위부터 분석합니다.

## 분석 순서

1. `references/analysis_scope_router.md` 기준으로 기능 단위인지 프로젝트 전체인지 분류합니다.
2. 분석 범위를 모듈, 패키지, 화면, 서비스, 특정 플로우, 프로젝트 전체 중 무엇인지 확정합니다.
3. UI 액션, 라우트, 리시버, 서비스, 스케줄러, 워커, IPC 엔드포인트 같은 진입점과 트리거를 찾습니다.
4. 프레젠테이션, 도메인, 데이터, 외부 연동 경계를 따라 흐름을 추적합니다.
5. 설정 파일, DI 바인딩, navigation graph, manifest, route, schema, migration, 테스트에서 숨은 연결을 확인합니다.
6. 정상 흐름과 실패 흐름, empty/loading/error 상태, 권한/네트워크/캐시 조건을 분리합니다.
7. 프로젝트 전체 역기획이면 기능 도메인 인벤토리, 화면/API 목록, 데이터/연동 지도, 운영/테스트 단서를 정리합니다.
8. 기획자나 신규 엔지니어도 이해할 수 있도록 기능 도메인 단위로 묶어 설명합니다.
9. 시퀀스, 상태 전이, 플로우차트가 이해를 줄이면 Mermaid를 사용합니다.

## 검증

- 설명한 각 흐름이 어떤 파일, 함수, 설정, 테스트에서 확인되는지 근거를 남깁니다.
- 불명확한 연결은 단정하지 말고, 확인이 필요한 지점으로 분리합니다.
- 코드에 없는 요구사항, 의도, 정책은 "추론"으로 분리하고 근거가 약하면 제외합니다.
- 후속 구현 제안이 필요하면 범위, 성공 기준, 검증 방법을 함께 적어 실행 가능한 단위로 만듭니다.
- 분석 과정에서 발견한 dead code, 중복 경로, 문서와 코드 불일치는 별도 메모로 남깁니다.
- 리빙독 갱신을 전제로 하면 `reverse_engineering_living_doc_bridge.md` 기준으로 어떤 문서에 반영할지, 반영하면 안 되는 추론은 무엇인지 분리합니다.

## 출력 규칙

- 각 기능은 Trigger -> Action -> Business Logic -> Data Source -> Result 순서로 설명합니다.
- 흐름을 입증하는 핵심 클래스나 파일을 함께 언급합니다.
- 코드 작성자가 아닌 사람도 이해할 수 있게 설명합니다.
- 아키텍처 코멘트는 동작 설명에 도움이 되거나 구조적 복잡성이 특이할 때만 짧게 덧붙입니다.
- 프로젝트 전체 역기획은 도메인 지도, 진입점 지도, 데이터/인터페이스 지도, 문서화 후보를 포함합니다.
- 문서화 요청이 있으면 마지막에 `Living Docs 갱신 후보`를 두고 대상 문서, 반영할 사실, 미확정 추론, 확인 필요를 나눕니다.
- 마지막에는 "확인한 근거"와 "아직 확인하지 못한 부분"을 짧게 구분합니다.
