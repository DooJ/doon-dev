# Linear QA

Linear를 장문 문서 저장소가 아니라 반복 가능한 QA 정의, 실행 상태, 증거, 버그 관계를 찾기 쉬운 운영 화면으로 사용한다. 제품별 세부 항목은 분리하되 팀·상태·공통 라벨·기록 방식은 여러 프로젝트에서 재사용한다.

## 발동 조건

- Linear에 QA 체크리스트, 테스트 케이스, 회귀 테스트, Full Run을 만들거나 갱신할 때
- 여러 제품이 함께 쓰는 QA 팀, 라벨, View, 템플릿, 상태 흐름을 설계할 때
- QA 중 발견한 버그를 개발 이슈와 연결하고 수정·재검증 이력을 남길 때
- 이전 실행을 보존하면서 다음 빌드나 환경에서 같은 QA를 다시 수행할 때
- QA에서 이슈가 발견된 항목을 `In Review`로 모아 보여 달라는 요청

단순히 로컬 테스트나 빌드를 실행하는 작업, QA와 무관한 일반 개발 이슈 관리, 코드 밖의 장문 테스트 문서만 작성하는 작업에는 적용하지 않는다.

## 핵심 모델

### 1. 팀과 이슈 키

- 여러 제품이 공용으로 쓰는 QA 기록은 별도 Linear 팀에서 관리하고, `QA-123` 형식이 필요하면 그 팀 identifier를 `QA`로 설정한다.
- 이슈 키는 팀 identifier로 결정된다. 라벨이나 제목을 바꿔 `QA-xx`를 만들 수 있다고 설명하지 않는다.
- 제품 결함은 QA 팀이 아니라 실제 수정 책임이 있는 개발 팀과 프로젝트에 일반 버그 이슈로 만든다.
- QA 팀을 새로 만들거나 identifier를 바꾸는 것은 workspace 구조 변경이므로 사용자의 승인 범위와 기존 팀을 먼저 확인한다.

### 2. 이슈 단위

- `Test Case`: 독립적으로 실행·판정 가능한 재사용 테스트 한 건
- `Regression`: 과거 결함이나 고위험 변경의 재발을 확인하는 재사용 테스트
- `Full Run`: 특정 build·commit·환경·장비에서 수행한 한 번의 전체 QA 실행 스냅샷
- 기본값은 재사용 Case와 실행당 Full Run 한 건이다. Case마다 별도 Execution 이슈를 복제하지 않는다.
- 규제, 감사, 출시 승인처럼 개별 실행의 불변 기록이 꼭 필요한 경우에만 Execution 하위 이슈를 추가한다.

### 3. 분류와 범위

- 공용 실행 레벨은 `Basic`, `Extended`, `Special` 세 가지로 유지한다.
- 공용 이슈 종류는 `Test Case`, `Regression`, `Full Run`으로 유지한다.
- 여러 제품에서 같은 의미로 쓰는 축은 workspace label group으로 만든다. 한 그룹에서는 한 값만 선택되게 한다.
- QA 팀 내부에서만 쓰는 개념은 team label로 제한한다.
- 제품 전용 모드, 장비, 플랫폼, 기능명은 해당 Linear Project, 프로젝트 템플릿 또는 꼭 필요한 최소 범위의 제품 전용 라벨로 관리한다. 다른 제품에도 전역 노출되는 라벨로 성급히 승격하지 않는다.

## 상태 계약

기존 QA 팀의 상태를 먼저 조회하고 아래 의미에 가장 가까운 상태를 재사용한다.

| 상태 | 의미 |
|---|---|
| `Todo` | 테스트 시작 전 또는 다음 테스트 시작 선언으로 초기화된 상태 |
| `In Progress` | 실제 테스트를 시작해 실행 중인 상태 |
| `In Review` | 테스트 중 이슈가 발견되어 확인·수정·재검증이 필요한 상태 |
| `Done` | 실제 테스트를 완료했고 기대 결과를 충족해 이상이 없는 상태 |

- `In Review`는 가능하면 기존 상태를 사용하고, 새로 만들 때는 Started 유형으로 둔다.
- 이슈 발생을 제목 접두사, 제목 변경, `needs-review` 같은 중복 라벨로 표현하지 않는다.
- 테스트 정의만 검토했거나 실행 준비만 한 Case는 `Done` 또는 `In Review`로 바꾸지 않고 `Todo`를 유지한다.
- 사용자 확인이나 정책 판단이 필요하다는 이유만으로 `In Review`를 사용하지 않는다. `In Review`는 실제 테스트에서 이슈를 발견했을 때만 사용한다.
- 이슈 수정·재검증 대기 중에는 `In Review`를 유지한다. 다음 테스트 또는 재검증을 시작하겠다고 선언하면 대상 Case를 `Todo`로 초기화하고, 실제 실행을 시작할 때 `In Progress`로 바꾼다.
- 실제 외부 차단 상태가 있고 팀에 기존 `Blocked` 상태가 있을 때만 사용한다. 이 스킬 때문에 상태를 늘리지 않는다.

## 내용 책임

QA Case 설명은 아래 세 부분만 기본으로 한다.

```markdown
## 목적
[무엇을 확인하는 테스트인지]

## 진행
[어떤 조건과 순서로 실행하는지]

## 기대 결과
[통과로 판정할 수 있는 결과]
```

- 설명에는 최신 테스트 정의를 둔다.
- build, 장비, 실제 결과, 로그, 버그, 재검증은 실행 코멘트에 둔다.
- 원인, 수정 내용, commit·PR, 개발 테스트는 개발 버그 이슈에 둔다.
- 같은 정보를 QA 설명, QA 코멘트, 개발 버그에 반복 복제하지 않는다.
- 실제 Linear 이슈·템플릿·코멘트를 생성하거나 갱신할 때는 [references/linear-qa-templates.md](references/linear-qa-templates.md)를 읽고 최소 형식을 사용한다.

## 실행 절차

1. 대상 workspace, QA 팀, 개발 팀, Linear Project, 기존 상태·라벨·View·템플릿을 조회한다.
2. 같은 목적의 팀, 라벨, View, 템플릿, Case가 있으면 재사용한다. 이름만 같고 의미나 필터가 다르면 덮어쓰지 않는다.
3. 이번 실행용 `Full Run`을 `Todo`로 만들고 build/version, commit, 환경, 장비와 범위를 스냅샷으로 남긴다.
4. 다음 테스트 시작을 선언하면 선택한 Case만 `Todo`로 초기화한다. 과거 코멘트와 과거 Full Run은 수정하거나 삭제하지 않는다.
5. 실제 첫 테스트 동작을 시작할 때 Full Run과 시작한 Case를 `In Progress`로 바꾸고 실제 실행 시작 시각을 남긴다. 결과·근거는 짧은 코멘트로 기록한다.
6. 실제 테스트가 이상 없이 끝나면 `Done`, 이슈가 발견되면 `In Review`로 둔다. 미실행 Case는 `Todo`를 유지한다.
7. 이슈가 발견되면 Full Run도 `In Review`로 바꾼다. 모든 Case가 이상 없이 확정되면 Full Run에 요약 코멘트를 남기고 `Done`으로 완료한다.

## 버그와 재검증

1. 제품 결함으로 확인되면 수정 책임 개발 팀과 해당 프로젝트에 버그를 만든다.
2. 개발팀의 기존 오류/버그 라벨과 템플릿을 우선 사용한다.
3. QA Case 또는 Full Run을 개발 버그에 `blocked by`로 연결하고 양쪽에 필요한 링크만 남긴다.
4. 개발 버그에는 재현, 영향, 원인, 수정, GitHub commit·PR 링크, 개발 검증 결과를 기록한다.
5. QA 코멘트에는 관찰 결과, 환경·장비, 증거, 연결된 버그, 재검증 결과만 기록한다.
6. 수정 뒤 원래 실패 코멘트를 고치지 않고 새 재검증 코멘트를 추가한다.
7. 재검증 통과 시 QA Case를 `Done`으로 바꾸고 관계와 코멘트는 이력으로 유지한다.

## 변경 이력

- 테스트 절차나 기대 결과가 바뀌면 Case 설명을 최신 기준으로 갱신하고, 변경 이유·적용 시작 Full Run·관련 요구사항 또는 버그를 코멘트로 남긴다.
- 과거 실행 결과를 새 기준에 맞게 소급 수정하지 않는다.
- 다음 실행은 최신 설명을 사용하고, Full Run 시작 코멘트에 적용한 Case 범위를 고정한다.
- 재현 가능성에 더 강한 스냅샷이 필요한 프로젝트만 Full Run 하위에 당시 절차 사본 또는 Execution 이슈를 둔다.

## View와 보고

- 공용 QA View: `Team = QA`를 기본으로 두고 Project, Level, Kind, Status로 필터링한다.
- 이슈 검토 View: `Team = QA`, `Status = In Review`로 만든다.
- 제품 View: `Project = 대상 제품`을 필수로 하고 QA 팀 이슈만 보고 싶으면 Team 필터를 추가한다.
- View 생성 도구가 없으면 임의 대체 View를 만들지 말고 정확한 수동 필터만 안내한다.

최종 보고는 완료 이슈 전체를 나열하지 않는다.

- 모두 정상: `QA 완료, 문제 없음.`
- 버그가 수정·재검증됨: 버그 수와 대표 링크만 한 문장으로 요약한다.
- 이슈 발생: `In Review` 항목만 식별자, 현상, 연결된 개발 버그를 짧게 나열한다. 통과 건수, 완료 영역, 전체 Case 목록은 사용자가 요청하지 않는 한 붙이지 않는다.
- 실행하지 못한 범위가 있으면 완료라고 말하지 않고 미실행 이유와 남은 범위만 보고한다.

## 금지 사항

- QA 결과만으로 개발 버그 이슈를 QA 팀에 중복 생성하지 않는다.
- 상태를 제목 접두사나 제목 변경으로 표현하지 않는다.
- Case 설명을 실행 일지나 로그 저장소로 사용하지 않는다.
- 매 실행마다 모든 Case를 Execution 이슈로 복제해 이슈 수를 폭증시키지 않는다.
- 제품 전용 라벨을 공용 workspace label로 무분별하게 만든다.
- 과거 실패를 통과로 덮어쓰거나 관계·코멘트를 삭제해 이력을 없애지 않는다.
- 모든 완료 항목을 사용자 최종 답변에 장황하게 나열하지 않는다.
- `In Review` 보고 앞에 통과 집계나 완료 영역을 다시 요약해 발생 이슈를 묻히게 하지 않는다.
