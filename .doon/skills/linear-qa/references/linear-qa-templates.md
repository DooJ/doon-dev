# Linear QA 최소 템플릿

실제 Linear 이슈와 코멘트를 만들 때 필요한 최소 형식이다. workspace의 기존 템플릿이 이 계약을 충족하면 새 템플릿을 만들지 않고 재사용한다.

## QA Case 설명

```markdown
## 목적
[확인할 동작과 이유]

## 진행
1. [사전 상태 또는 시작점]
2. [핵심 행동]
3. [판정 지점]

## 기대 결과
[관찰 가능한 통과 조건]
```

## Full Run 설명

```markdown
## 목적
[이번 실행의 대상과 목적]

## 기준
- Build/Version: [값]
- Commit: [SHA 또는 URL]
- 환경: [서버/OS/권한 등 필요한 값]
- 장비: [식별 가능한 이름]

## 범위
- Basic: [전체 또는 Case 링크]
- Extended: [전체/선택/미실행 사유]
- Special: [선택 Case 또는 미실행 사유]

## 완료 조건
- 선택한 Case 결과가 확정됨
- 발견 버그가 개발 이슈와 연결됨
- `In Review` 항목이 해소됨
```

## 실제 실행 시작 코멘트

```markdown
실제 실행 시작: [일시]
기준: [build/version, commit]
대상: [환경/장비]
범위: [Case 링크 또는 개수]
```

## Case 결과 코멘트

```markdown
Run: [QA Full Run 링크]
결과: 통과 | 이슈 발생 | 미실행
근거: [짧은 관찰 결과와 로그/스크린샷 링크]
연결: [개발 버그 또는 없음]
```

## 절차 변경 코멘트

```markdown
테스트 정의 변경: [변경 요약]
이유: [요구사항/버그/환경 변화]
적용: [이 Full Run부터]
근거: [관련 링크]
```

## 재검증 코멘트

```markdown
재검증: [일시, build/version, commit]
대상 버그: [개발 이슈 링크]
결과: 통과 | 이슈 발생
근거: [관찰 결과와 증거 링크]
```

## 개발 버그 연결 코멘트

QA 쪽:

```markdown
개발 버그: [TEAM-123 링크]
관찰: [실패 현상]
재검증 조건: [수정 build 또는 필요한 조건]
```

개발 버그 쪽에는 기존 팀 템플릿을 우선 사용하고 아래 정보만 빠지지 않게 한다.

- 관련 QA Case와 Full Run 링크
- 재현 환경과 절차
- 기대 결과와 실제 결과
- 영향
- 원인과 수정 내용
- GitHub commit 또는 PR 링크
- 개발 검증 결과

## Full Run 종료 코멘트

정상 완료:

```markdown
QA 완료, 문제 없음.
```

버그가 있었으나 해결됨:

```markdown
QA 완료. 발견 버그 [N]건은 수정·재검증 완료: [대표 이슈 링크]
```

이슈가 남음:

```markdown
QA 이슈 발생 [N]건.
- [QA-123]: [현상 요약] / [개발 버그 링크 또는 미등록]
```

`In Review` 보고에는 통과 건수, 완료 영역, 전체 Case 목록을 앞뒤로 덧붙이지 않는다. 사용자가 집계를 따로 요청한 경우에만 제공한다.

미실행 범위가 남음:

```markdown
QA 미완료. 남은 범위: [Case 또는 영역]
사유: [환경/권한/장비/외부 의존성]
```
