# 에러 대응 분석

- Kotlin nullability, 예외 처리, 방어 코드가 핵심인 인시던트라면 `../kotlin_basics/SKILL.md`를 불러옵니다.
- 근본 원인을 입증하는 데 필요한 최소한의 파일과 로그만 읽습니다. 근거가 없으면 추측하지 않습니다.
- 수정은 재현 가능한 실패 조건을 좁힌 뒤 최소 패치로 시작합니다. 원인을 가리는 catch-all 처리나 광범위한 리팩토링은 마지막 수단으로만 제안합니다.

## 번들 레퍼런스
- 로그가 길거나 원인 후보가 여러 개이거나 build/test/runtime/integration/deploy 실패를 재현·수정·검증까지 이어가야 하면 `references/debugging_triage_playbook.md`를 읽습니다.
- 짧은 에러 메시지 해석이나 단일 원인이 명확한 실패에는 reference를 읽지 않고 본문 기준만 적용합니다.

## 프리앰블

- 실패 유형이 `build`, `test`, `runtime`, `integration` 중 무엇인지 먼저 분류합니다.
- 사용자가 수정까지 원하는지, 원인 분석만 원하는지 먼저 구분합니다.
- 재현 조건이 필요한 문제라면 실행 환경, 입력값, 직전 상태 변화를 먼저 정리합니다.
- 로그가 길다면 먼저 시간대, 프로세스, 스레드, 첫 실패 프레임, 사용자 행동, 배포 버전을 기준으로 필요한 구간을 압축합니다.

## 분석 순서

1. 먼저 `FATAL`, `Exception`, `Caused by`, 종료 코드, 실패한 테스트, 또는 코드베이스 내부의 첫 실패 프레임을 찾습니다.
2. 관련된 정확한 파일, 클래스, 함수, 라인을 식별합니다.
3. 스레드, 생명주기 단계, 비동기 콜백, 네트워크나 DB 경계, 직전 상태 변화 등 런타임 컨텍스트를 재구성합니다.
4. 직접적인 발화 지점과 구조적인 원인을 분리해서 정리합니다.
5. 영향 범위가 특정 사용자, 특정 OS/API, 특정 데이터 상태, 특정 환경 변수, 특정 릴리즈에 한정되는지 확인합니다.
6. 대응책은 두 층위로 나눠 제시합니다.
   - Hotfix: 즉시 적용 가능한 방어 코드나 실패 격리 조치
   - Solid fix: 잘못된 상태나 흐름 자체를 제거하는 구조적 수정

## 검증

- 원인 후보가 여러 개면 가장 증거가 강한 순서로 정리하고, 서로를 배제하는 조건을 함께 적습니다.
- 수정 방향을 제안할 때는 어떤 로그, 테스트, 재현 경로로 검증할지 함께 제시합니다.
- 패치가 가능하면 "재현 -> 수정 -> 같은 경로로 재검증" 순서가 성립하는지 확인합니다.
- 명령 실행으로 재현 또는 검증이 가능하면 관련 테스트/빌드 명령을 실행하고 결과를 요약합니다.
- 재현 불가능한 장애는 추가로 필요한 로그, 계측, 사용자 행동 정보, 서버/클라이언트 상관 ID를 명시합니다.

## 출력 규칙

- 에러 종류, 실패 위치, 가장 가능성 높은 근본 원인을 보고합니다.
- 로그만으로 완전히 증명되지 않는 부분은 추론임을 명확히 표시합니다.
- 코드 경로가 충분히 명확해 안전하게 수정할 수 있을 때는 구체적인 패치 방향을 포함합니다.
- 마지막에는 생명주기, 상태 소유권, 데이터 흐름 관점의 재발 방지 가이드를 덧붙입니다.
- 사용자 영향, 임시 우회, 영구 수정, 검증 결과를 구분해 빠르게 실행 가능한 형태로 정리합니다.
