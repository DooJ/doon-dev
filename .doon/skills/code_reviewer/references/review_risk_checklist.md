# Review Risk Checklist

변경사항, PR, 설계 변경, 특정 파일 리뷰에서 실제 결함·회귀·테스트 누락을 빠르게 찾기 위한 체크리스트다. 리뷰 범위가 넓거나 사용자 영향, 데이터, 보안, 배포 위험이 있는 경우에 읽는다.

## 1. 리뷰 범위 분류

| 범위 | 우선 확인 |
|---|---|
| 단일 파일 | 주변 호출부, 입력/출력 계약, 예외 흐름 |
| diff/PR | 비교 기준, 새로 생기거나 악화된 결함, 변경 의도, 영향 범위, 테스트, 배포/마이그레이션 |
| 설계 리뷰 | 책임 경계, 데이터 소유권, 실패 격리, 확장 비용 |
| Hotfix 리뷰 | 재현 조건, 최소 수정, 회귀 테스트, 임시 우회 제거 계획 |

## 2. 결함 위험

| 영역 | 질문 |
|---|---|
| 상태 | nullable, 초기화 순서, lifecycle, stale state가 안전한가? |
| 데이터 | 스키마 변경, migration, 캐시, 동기화, 정렬/필터 기준이 깨지지 않는가? |
| 경계값 | 0개, 1개, 대량, null, 빈 문자열, 중복, 권한 없음이 처리되는가? |
| 동시성 | race, 중복 요청, 취소, timeout, 재시도, idempotency가 안전한가? |
| 오류 | 실패를 삼키거나 잘못된 성공 상태로 바꾸지 않는가? |
| 성능 | hot path, 메인 스레드, 반복 I/O, N+1, 큰 payload 문제가 없는가? |
| 보안/개인정보 | 권한, 입력 검증, 로그 노출, secret, PII 저장/전송이 안전한가? |

## 3. 테스트 공백

| 변경 유형 | 필요한 검증 |
|---|---|
| 조건 분기 추가 | happy path, false branch, edge case |
| 데이터 모델 변경 | migration, backward compatibility, serialization |
| UI 상태 변경 | loading, empty, error, success, accessibility |
| API/네트워크 | success, client error, server error, timeout, retry |
| 권한/인증 | unauthorized, expired session, role mismatch |
| 배치/자동화 | dry-run, idempotency, partial failure |

## 4. 리뷰 finding 작성 기준

좋은 finding은 아래를 포함한다.

- 파일과 라인
- 실제로 실패할 수 있는 입력, 상태, 호출 순서
- 변경 리뷰라면 기준 버전과의 차이 및 영향받는 호출부. 전체 감사의 기존 결함과 구분
- 사용자 영향 또는 운영 영향
- 왜 현재 코드가 그 상황을 막지 못하는지
- 가능한 검증 방법 또는 테스트 방향

피해야 할 것:

- 취향성 스타일 지적을 심각한 결함처럼 쓰기
- 코드 근거 없이 “아마 위험함”으로 끝내기
- 의도된 동작 변경을 오류로 단정하거나 같은 원인을 여러 finding으로 반복하기
- 요청 범위 밖의 대규모 리팩토링을 주된 결론으로 만들기
- 테스트가 없어도 어떤 테스트가 필요한지 말하지 않기

## 5. 심각도 기준

| 등급 | 기준 |
|---|---|
| P0 | 데이터 손상, 보안 사고, 서비스 중단, 배포 즉시 차단 필요 |
| P1 | 주요 사용자 흐름 실패, 넓은 회귀, 중요한 데이터/권한 오류 |
| P2 | 특정 조건의 버그, 중간 수준 회귀, 테스트 공백이 큰 변경 |
| P3 | 유지보수성, 명확성, 낮은 가능성의 edge risk |

## 6. 최종 점검

- findings가 심각도순으로 정렬되어 있는가?
- 각 finding이 실제 코드 경로에 묶여 있는가?
- 스타일 의견과 결함 위험을 구분했는가?
- 발견 사항이 없을 때도 남은 테스트/검증 공백을 적었는가?
