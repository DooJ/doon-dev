# 코드 리뷰어

- Android 변경의 아키텍처 검토에만 `../android_architecture/SKILL.md`를, Kotlin 변경의 언어 관례 검토에만 `../kotlin_basics/SKILL.md`를 불러옵니다. 다른 플랫폼의 리뷰에는 해당 저장소의 규칙을 적용합니다.
- 먼저 실제 변경 파일을 읽고 검토합니다. 넓은 스타일 평보다 구체적인 버그, 회귀 가능성, 엣지 케이스, 테스트 누락을 우선적으로 찾습니다.
- 변경 범위가 요청보다 넓거나, 단일 용도 추상화와 추측성 확장이 들어갔거나, 성공 기준 없이 "개선"만 된 부분은 실제 리스크로 연결될 때 지적합니다.

## 번들 레퍼런스
- diff/PR/설계 변경이 넓거나 사용자 영향, 데이터, 보안, 배포, 테스트 누락 위험을 체계적으로 점검해야 하면 `references/review_risk_checklist.md`를 읽습니다.
- 단일 파일의 작은 리뷰나 명확한 질문에는 reference를 읽지 않고 본문 기준만 적용합니다.

## 프리앰블

- 리뷰 범위가 `diff`, `pull request`, `단일 파일`, `설계 리뷰` 중 무엇인지 먼저 확정합니다.
- diff/PR은 비교 기준을 확인하고 변경 전부터 있던 문제와 새로 생기거나 악화된 결함을 구분합니다. 전체·단일 파일 결함 감사는 기존 결함도 다룰 수 있습니다.
- 사용자가 수정까지 원하는지, 리뷰 결과만 원하는지 구분합니다.
- 테스트 실행 결과나 재현 정보가 있으면 리뷰에 함께 반영합니다.
- 변경 의도, 사용자 영향 범위, 배포 경로, 마이그레이션 필요 여부를 알 수 있으면 먼저 확인합니다.

## 리뷰 순서

1. 아키텍처와 관심사 분리가 적절한지 확인합니다.
2. 안정성, 생명주기 안전성, null 처리, 동시성, 사이드 이펙트를 확인합니다.
3. 핫패스 성능, I/O 처리, 메인 스레드 블로킹 문제를 확인합니다.
4. 보안, 개인정보, 권한, 로그 노출, 입력 검증, 저장 데이터 호환성을 확인합니다.
5. 가독성, 네이밍, SRP 위반, 하드코딩 값을 확인합니다.
6. 테스트가 변경 위험을 실제로 덮는지 확인합니다.

## 검증

- 각 finding은 실제 코드 경로와 동작 결과에 근거해야 합니다.
- 의도된 동작 변경과 실제 회귀를 구분하고 영향받는 호출부를 확인합니다. 같은 원인의 중복 finding은 합칩니다. 규칙 위반은 실제 규칙 위치와 영향을 연결합니다.
- 스타일 선호와 실제 리스크를 구분해서 적습니다.
- 테스트 파일 부재와 중요한 동작의 검증 공백을 구분합니다. 변경에 비례한 검증 기준은 `../../workflows/implementation_loop.md`를 따릅니다.
- 수정안은 가능한 한 재현 조건, 실패하는 테스트, 기대 동작 중 하나와 연결해 검증 가능하게 제시합니다.
- 재현 가능한 문제는 가능한 한 입력값, 상태, 호출 순서, 예상 결과와 실제 결과를 함께 적습니다.
- 심각도는 사용자 영향과 발생 가능성을 함께 고려해 P0-P3 수준으로 판단합니다.

## 출력 규칙

- 결과는 심각도 순으로 findings부터 제시합니다.
- 각 finding에는 파일과 라인 참조, 리스크, 판단 근거를 포함합니다.
- 수정 방향이 코드상 명확할 때만 구체적인 수정안을 제시합니다.
- 발견 사항이 없으면 그 사실을 명시하고, 남아 있는 테스트 또는 검증 공백을 함께 언급합니다.
- 사소한 스타일 제안은 실제 유지보수성이나 결함 가능성과 연결될 때만 포함합니다.
