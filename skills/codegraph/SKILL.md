# 코드그래프

이 스킬은 두 범위를 구분한다. DooN의 `Sources`는 외부 **원본**을 보관하고, 각 프로젝트의 `codebase-map/<분석 범위>/<버전>/`은 분석 **결과**를 보관한다. Graphify와 Archify의 원본 `SKILL.md`는 수정하지 않는다. 별도의 DooN External 플러그인을 만들지 않는다.

## 요청 분기와 준비 확인

- **`코드그래프 세팅해`**: 아래 외부 원본·전역 설치 절차를 실행하고, 각 에이전트에서 실제 사용 가능 여부를 확인한다. 설치만 요청했다면 프로젝트의 `codebase-map/`을 만들거나 코드 분석을 시작하지 않는다. 이미 설치됐다면 출처·버전·동작 상태를 확인하고 필요한 부분만 복구한다.
- **`코드그래프 분석해` / `코드그래프 진행해`**: 대상 프로젝트를 정하고 먼저 준비 상태를 점검한다. 현재 에이전트에서 Graphify와 Archify의 검토된 원본 checkout, 필요한 스킬·CLI와 의존성, 실제 호출 경로가 유효해야 한다. DooN Dev의 `codegraph` **관리 스킬만 설치된 상태는 준비 완료가 아니다.** Obsidian 앱 설치는 Markdown 볼트 생성의 필수 조건이 아니다.
- **`<기능> 코드그래프 분석해`**: 같은 분석 범위의 기존 지도와 기능 흐름 목록을 읽고 해당 흐름을 세부 동작까지 확장한다. 아직 전체 지도가 없다면 요청한 기능과 연결된 구성요소·경계의 기준 지도를 먼저 만든다. 기능 이름을 새 분석 범위나 독립 버전으로 자동 해석하지 않는다.
- 준비가 부족하면 빠진 도구·경로를 구체적으로 알리고 **`코드그래프 세팅해`**를 먼저 요청하도록 안내한다. 분석 요청만으로 외부 스킬을 자동 설치하거나 빈 `codebase-map/`을 만들지 않는다. 한 요청에서 세팅과 분석을 모두 명시했다면 세팅을 검증한 뒤 분석을 이어간다.
- 분석 대상이 명확하면 현재 프로젝트를 사용한다. 여러 프로젝트를 한 지도로 묶을 때는 결과를 저장할 공통 프로젝트 루트를 확인한다. 대상이나 저장 루트가 불분명하면 경로를 확인한다. `진행해`는 요청한 **분석 범위**의 기존 버전이 있으면 갱신하고, 없으면 그 범위에서 `v1.0.0`을 시작한다. 다른 범위의 결과를 덮어쓰지 않는다.

## 외부 원본과 에이전트 배포

`코드그래프 세팅해`처럼 사용자가 원본 연결·설치·업데이트를 요청한 경우에만 수행한다.

1. 현재 환경의 `AGENTIC_ROOT`를 확인한다. 공식 원본은 [Graphify-Labs/graphify](https://github.com/Graphify-Labs/graphify)와 [tt-a1i/archify](https://github.com/tt-a1i/archify)에서 재확인한다. 동명 프로젝트를 추측해 선택하지 않는다.
2. 원본을 `<AGENTIC_ROOT>/Sources/external/graphify`, `<AGENTIC_ROOT>/Sources/external/archify`에 별도 checkout으로 받거나 기존 checkout을 갱신한다. 출처 URL·commit·라이선스·검토일을 로컬 목록에 남긴다. `Sources/selection.json`은 DooN 소유 플러그인 선택 상태이므로 외부 저장소를 끼워 넣지 않는다.
3. 실행·설치 전에 대상 스킬과 스크립트, 의존성을 `skill-inspector` 또는 같은 수준의 읽기 전용 검토로 확인한다. 검토가 끝나기 전에는 원본 설치 스크립트를 실행하지 않는다.
4. 검토한 원본에서 Codex·Claude·Antigravity의 **사용자 전역** 설치 경로와 명령을 확인해 각각 적용한다. 원본 checkout과 설치본의 버전·내용이 일치하는지 확인하고, 설치 명령이 최신 원격 버전을 다시 받는다면 고정된 원본을 설치할 수 있는 방법을 먼저 찾는다. DooN Dev 플러그인은 이 **관리 스킬**을 배포하며, 외부 스킬·CLI의 플랫폼별 설치는 이 스킬이 관리하는 별도 상태다. Graphify의 프로젝트 설치나 `AGENTS.md`·`CLAUDE.md`를 고치는 상시 지침 명령은 실행하지 않는다. DooN 생성 어댑터의 소유권을 보존한다.
5. 각 에이전트에서 설치된 스킬·도구의 실제 경로와 버전을 확인한다. 지원되지 않는 플랫폼이나 실패한 설치는 성공으로 표시하지 않는다. DooN Dev 관리 스킬 자체의 변경은 이 저장소의 버전 관리와 플러그인 배포 절차를 따른다.

## 프로젝트 산출물

프로젝트 안에는 `codebase-map/` **실제 폴더 하나**를 두고 그 아래에 요청 범위별 이름을 둔다. 범위 이름은 사람이 알아볼 수 있는 한 단계 폴더 이름으로 정한다. 예를 들어 같은 코드 저장소에서도 `보이미 생태계`와 `보이미 메뉴`는 서로 독립된 지도와 `v1.0.0`부터의 버전을 가진다. 버전 폴더는 실제 산출물을 담으며, 범위 폴더의 `VERSION.md`는 그 범위의 전체 이력을 요약한다.

```text
<project>/
├── codebase-map/
│   ├── 보이미 생태계/
│   │   ├── version-ledger.json  # 이 범위만의 버전·구성요소 이력
│   │   ├── VERSION.md          # 이 범위의 전체 버전 요약
│   │   └── v1.0.0/
│   │       ├── graphify-out/   # 상세 그래프·필요시 overview/
│   │       ├── archify/        # 검증된 다이어그램
│   │       ├── vault/          # 이 범위의 독립 Obsidian 볼트
│   │       └── VERSION.md      # 이 버전의 작업·승계 요약
│   └── 보이미 메뉴/
│       ├── version-ledger.json
│       ├── VERSION.md
│       └── v1.0.0/...
└── graphify-out  # 기존 무범위 결과가 있을 때만 보존
```

1. 프로젝트 루트와 기존 `codebase-map/`, 루트 `graphify-out`, `.archify`, Obsidian 볼트의 존재를 먼저 확인한다. 요청한 범위 이름을 정하고 이 스킬의 `scripts/project_layout.py --project <project> --scope <범위> status`로 같은 이름의 지도와 최상위 무범위 결과를 점검한다. 새 범위는 `prepare`로 범위 폴더만 만든다. 기존 무범위 결과는 어느 범위에 속하는지와 내부 링크·생성기 경로를 확인하기 전에는 자동 이동하거나 새 범위로 간주하지 않는다.
2. `scripts/version_ledger.py --project <project> --scope <범위> init`으로 해당 범위의 `v1.0.0/`을 만들거나 기존 범위의 현재 버전을 확인한다. Graphify는 **프로젝트 루트**에서 실행하되 매번 `GRAPHIFY_OUT`에 이 버전의 `graphify-out/` **절대경로**를 지정한다. 검토한 원본에서는 추출과 증분 갱신 모두 이 경로에 기록된다. 조회·군집화·내보내기도 명시적 `--graph` 경로 또는 같은 환경변수로 해당 범위만 사용한다. 새 범위의 작업을 위해 루트 `graphify-out` 링크를 바꾸거나 다른 범위의 그래프를 덮어쓰지 않는다. 원본 `graph.json`·`graph.html`은 코드 수준 탐색 자료이며, 단일 프로젝트에서도 곧바로 읽기 쉬운 구조 지도가 된다고 가정하지 않는다. 사용자에게 보여줄 상세 `graph.html`과 `GRAPH_REPORT.md`를 만들 때 `cluster-only --no-label`을 기본으로 사용하지 않는다. `--no-label`은 군집 이름을 `Community N`으로 남긴다. 모델 백엔드가 없거나 로그인되지 않은 경우에도 검토한 Graphify는 해당 옵션 없이 재군집화하면 대표 허브 심볼명으로 대체한다. 임시 추출에서 `--no-label`을 썼다면 최종 전달 전에 해당 옵션 없이 다시 군집화하고 이름을 확인한다.
3. [개요 지도 기준](references/overview-graph.md)에 따라 분석 범위를 구분한다. **단일 프로젝트**는 원본 화면에서 요청한 모듈·흐름을 읽을 수 있는지 확인하고, 어렵다면 코드 근거형 개요 JSON·HTML을 추가한다. **여러 프로젝트·앱·서비스**를 하나의 시스템으로 보는 요청은 디렉터리나 저장소 배치와 관계없이 프로젝트 경계와 확인된 교차 연결을 담은 통합 개요 HTML을 필수로 만든다. Graphify의 `export html --graph` 등 검증된 경로로 **현재 범위·버전**의 `graphify-out/overview/`에 출력하고 원본 상세 `graph.html`을 덮어쓰지 않는다. 개요 JSON만 만들어 두거나 상세 AST HTML을 통합 지도로 소개하지 않는다.
4. Archify는 에이전트가 정리한 구조를 타입별 JSON 다이어그램으로 작성·검증하고 HTML로 내보내는 도구다. 문서·설명만으로도 다이어그램을 만들 수 있지만, **프로젝트 코드그래프**에서는 현재 코드와 Graphify 조회 결과 및 개요 지도를 기본 근거로 삼고 기존 문서는 있을 때만 대조한다. 문서가 없다는 이유로 선행 문서 작성을 요구하지 않는다. 기본 분석에서는 전체 구조와 기능군 간 흐름을 읽을 수 있게 그리고, 분기나 프로젝트 경계가 중요한 흐름은 필요한 sequence·dataflow 등으로 보강한다. 모든 함수나 단순 경로마다 그림을 만들지는 않는다. 현재 구조인지 계획안인지, 어떤 흐름을 그릴지 코드와 요청만으로 결정할 수 없을 때만 필요한 범위를 질문한다. Graphify 산출물이 Archify에 자동 입력된다고 가정하지 않는다. 저장소에서 확인된 사실과 문서·요구사항에만 있는 구상은 다이어그램과 설명에서 구분한다. 코드 근거를 주장하는 다이어그램은 원본 Archify 지침의 source evidence·revision 검증 절차를 따른다. 출력 경로는 **현재 범위·버전**의 `archify/<유형>-<이름>-<시각>/`로 처음부터 지정한다. 기존 `.archify` 산출물은 내부 참조와 검증 결과를 확인하기 전에는 자동 이동하지 않는다.
5. **현재 범위·버전**의 `vault/`는 Graphify의 `export obsidian` 결과를 그대로 쓰지 않고, 코드·Graphify 그래프/보고서·개요 지도·Archify 구조도·기존 문서를 근거로 **별도 저작**한다. Graphify 내보내기는 노드 속성과 연결 중심이므로 최종 볼트의 설명을 대신하지 못한다. 원시 노트가 필요하면 현재 버전의 `graphify-out/obsidian/`에만 내보내고 최종 볼트에는 직접 덮어쓰지 않는다.
6. [볼트 작성 기준](references/vault-authoring.md)에 따라 탐색 시작점, 현재 시스템 지도, **기능 흐름 목록과 범위 내 흐름별 중간 깊이 분석**, 구성요소·필요한 상세 색인을 작성한다. 코드에서 확인한 사실과 추정·운영 확인 필요 항목을 구분하고 각 핵심 주장에 소스나 그래프 근거를 연결한다. 모든 그래프 노드를 노트로 복제하거나 기존 보이미 볼트의 폴더 수·노트 수를 목표로 삼지 않는다. 기존 볼트와 `.obsidian` 설정, 수동 노트, Graphify 소유 노트는 소유권을 확인해 보존한다.
7. `.graphifyignore`에 `codebase-map/` 등 생성물 제외가 필요한지 확인해 재귀 분석을 막는다. Git에는 그래프의 공유할 데이터와 확정 다이어그램·볼트 노트만 프로젝트 정책에 따라 포함한다. 기기 절대경로, AST 캐시, 개인별 볼트 UI 상태는 제외한다. 여러 버전의 대형 그래프가 쌓일 수 있으므로 이전 버전 파일의 보존·Git 추적 범위도 프로젝트 정책에 맞춘다.

## 기본 분석과 기능 심화

- 범위 전체 요청에서는 화면·사용자 행동, API/메시지 진입점, 백그라운드 작업, 주요 상태 변경을 조사해 **기능 흐름 목록**을 먼저 만든다. 같은 목적의 엔드포인트·메서드는 하나의 기능 흐름으로 묶되, 다른 사용자 결과나 외부 시스템 경계를 가진 흐름을 편의상 합치지 않는다. 발견한 진입점은 흐름에 연결하거나 제외·미확인 이유를 적어 누락을 드러낸다.
- 기본 분석은 각 기능 흐름의 **시작 조건 → 주요 처리 단계와 구성요소 경계 → 결과**, 중요한 분기·실패 경로, 대표 코드·계약 근거, 확인하지 못한 구간까지 작성한다. 함수 내부 구현, 모든 필드 변환, 예외별 복구 절차를 일괄 확장하지 않는다. 대상이 크면 기능군별로 나눠 진행하고 미완료 흐름을 목록에 남긴다. 완료한 일부 흐름을 전체 완료로 보고하지 않는다.
- 사용자가 기능을 지정하면 같은 범위의 흐름을 세부 분석한다. Graphify에서 관련 심볼·호출 경로를 좁히고 코드를 대조해 조건·데이터 변환·상태 변경·오류·재시도·부작용·수정 및 검증 지점을 추적한다. Archify는 분기나 시간 순서의 이해에 도움이 되는 해당 흐름의 diagram을 추가하고, Obsidian의 기존 흐름 노트와 구성요소·계약 링크를 확장한다. 기존 전체 지도를 재추출해야 하는 코드 변경이 없다면 재사용한다.
- 기존 지도에 축적하며 [프로젝트 버전 관리 기준](references/project-versioning.md)에 따라 실제 변경 구성요소를 기록한다. 기능 심화만으로 새 분석 범위나 전체 버전을 자동 생성하지 않는다.

## 프로젝트 단위 버전

[프로젝트 버전 관리 기준](references/project-versioning.md)에 따라 **분석 범위마다 버전 하나씩** 관리한다. Graphify·Archify·Obsidian은 각각 독립적으로 수정될 수 있으므로, 현재 범위·버전 아래에 검증된 산출물의 실제 실행 시각과 지문을 누적한다. 다른 범위의 버전은 독립적이며 구성요소를 다시 실행할 때마다 전체 버전을 올리지 않는다.

- 범위 폴더를 준비한 뒤 `scripts/version_ledger.py --project <project> --scope <범위> init`으로 그 범위의 `v1.0.0`을 연다. 기존 무범위 결과의 과거 시각은 추정하지 않는다.
- 각 구성요소의 이번 결과를 확인한 뒤 `record --component ... --artifact ... --note ...`로 실제 변경 파일을 기록한다. 지문이 같으면 새 이력이 생기지 않는다. 미완료·미검증 결과도 기록하지 않는다.
- 그래프·다이어그램·볼트를 함께 참조하는 전체 기준을 바꿀 때 `bump --level patch|minor|major`로 새 버전을 연다. 새 기준 작업 후 규모가 예상보다 크거나 작으면 `reclassify --level ...`로 **진행 중인 최신 버전**만 재분류한다. 닫힌 버전의 기록은 보존한다.
- 각 범위의 `version-ledger.json`이 이력의 원본이고 범위·버전 폴더의 `VERSION.md`는 파생 요약이다. 둘을 수작업으로 따로 편집하지 않는다. 버전별 폴더는 그 버전에서 생성한 산출물을 담고, 새 버전에서 실행하지 않은 구성요소는 이전 버전 결과를 이력상 승계한다. 같은 버전 안의 시각별 지문은 변경 추적이며 별도 백업이 아니다.

## 완료 단계

별도의 애프터 스킬이 자동 발동하기를 기다리지 않는다. 이 스킬의 같은 실행에서 원본 그래프 조회, 최종 상세 HTML·보고서의 `Community N` 자리표시자 유무와 실제 군집 이름, 범위에 맞는 개요 HTML의 실제 노드·관계 표시와 대표 근거, 다이어그램 열기, 볼트 시작점·기능 흐름 목록·각 흐름의 시작·결과·경계·분기·근거·미확인 구간, 경로·제외 설정과 전체 버전 및 구성요소별 최신 실제 갱신 시각을 확인한다. 발견한 진입점이 흐름 또는 제외·미확인 목록에 연결되는지 점검한다. 대표 허브 심볼명으로 자동 대체했다면 의미형 구성요소 이름과 다를 수 있음을 보고하고 개요 지도를 주 진입점으로 제시한다. 단일 프로젝트에서 개요를 생략했다면 원본 화면으로 요청을 읽을 수 있는 이유를, 여러 프로젝트라면 교차 연결의 확인·추정 상태를 보고한다. 실제 산출 위치와 미완료 항목도 알린다. `docs/`와 `publish/`로 자동 복사하지 않는다.
