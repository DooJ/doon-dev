# 분석 데이터와 멀티 볼트 계약

코드그래프의 재사용 가능한 결과는 JSON 데이터다. Obsidian 볼트와 HTML 화면은 이 데이터의 목적별 탐색 뷰다. Graphify 그래프를 그대로 최종 지식 모델로 삼지 않고, Archify 도형을 코드 실행 근거로 승격하지 않는다.

## 버전 폴더의 소유권

```text
<version>/
├── capability-map.json       # 프로젝트 역할·기능·관계의 저작 입력
├── graphify-out/             # 이번 버전에서 실행했다면 상세·개요 원본
├── archify/                  # 이번 버전에서 실행했다면 구조도
├── method-graph/             # 이번 버전에서 작성했다면 메서드·흐름 데이터
├── data/catalog.json        # 현재 분석이 참조하는 원본·지문·수치·안정 ID
├── generation-manifest.json # 생성 파일 소유권과 입력 지문
└── vaults/                  # 컨테이너, .obsidian 없음
    ├── registry.json
    ├── system/              # 여러 프로젝트의 상위 연결 볼트
    ├── <project-a>/         # 독립 솔루션 볼트
    └── <project-b>/
```

단일 프로젝트는 `vaults/<project>/` 하나로 시작할 수 있다. 여러 프로젝트는 상위 볼트 하나와 요청한 프로젝트 각각의 볼트를 둔다. 목적별 볼트를 추가할 때는 중복 소유할 노트를 정하고 `registry.json`에 고유 ID·폴더명·용도·홈을 등록한다. 하위 볼트를 상위 볼트 안에 넣지 않는다. 이전 버전의 `vault/`는 삭제·자동 이동하지 않는다.

`data/catalog.json`은 `schema_version: 1`, 분석 범위·버전, `sources`의 상대경로와 SHA-256, `counts`, 안정 ID 규칙, `vault_registry: "../vaults/registry.json"`을 가진다. 입력 경로는 `data/catalog.json`의 폴더를 기준으로 해석한다. 같은 범위의 이전 버전을 승계할 수 있지만 반드시 실제 경로·지문을 기록하고 `CHANGE_REPORT.md`에 새 분석이 아님을 밝힌다. 원본에 사용자·운영 비밀을 넣지 않는다.

`vaults/registry.json`은 `schema_version: 1`과 `vaults` 목록을 가진다. 각 항목에는 `id`, `kind` (`hub`·`solution`·목적별 종류), 버전 폴더 상대 `path`, 고유한 `vault_name`, `home`을 기록한다. 솔루션 볼트 ID 집합은 `capability-map.json`의 프로젝트 ID 집합과 같아야 한다. 예시와 검사 구현은 `scripts/check_multi_vault.py`를 따른다.

## 메서드·계약 데이터

- 전체 코드 색인은 메서드마다 안정 ID, 소속 프로젝트, 클래스·시그니처, 소스/아카이브 위치, 추출 출처를 둔다. 관계는 출발·도착 ID, 유형, 위치, 정적 후보 또는 확인 상태를 둔다. Graphify AST에 없는 WAR/JAR는 바이트코드·설정 조사 결과를 별도 출처로 보존한다.
- 사람이 검토한 흐름은 안정 흐름 ID와 시작·결과·분기, 참여 노드·연결 ID를 가진다. 각 연결에는 양쪽 구현이나 계약 근거, 상태(`verified_static`, `conditional`, `runtime_unknown`, `blocked` 등), 데이터 변환·상태 변경·실패 조건을 기록한다. HTTP·MQTT·Bluetooth·Intent·DB 같은 경계는 메서드 호출과 구별한 노드로 표현한다.
- 자동 호출 후보, 메서드 이름 일치, 서버 인터페이스 구현 후보는 실행 확정이 아니다. 운영 전달·배포 버전·권한·DB 값이 확인되지 않은 지점은 별도 상태로 남긴다. 흐름에서 건너뛴 구간을 묵시적으로 연결하지 않는다.
- 솔루션마다 주요 기능이 검토된 메서드 경로로 이어지거나 미검토 이유·남은 범위에 나타나야 한다. 메서드 총수와 검토된 메서드 수를 함께 적는다. 수천 개 노트를 기계적으로 만들었다는 사실만으로 심화 분석을 주장하지 않는다.

## 볼트 투영

상위 볼트는 각 솔루션의 **로컬 대리 노트**를 통해 핵심 계약과 교차 흐름을 네이티브 그래프에 표시한다. 각 솔루션 볼트는 자기 역할·기능, 검토된 메서드, 직접 닿는 경계와 상대 솔루션의 로컬 대리 노트, 관련 흐름을 가진다. 노트에는 안정 ID와 원본 위치·상태를 표시하고, 직접 경로의 조건·변환·상태·오류·재시도·부작용을 사람이 읽을 수 있게 설명한다. 목적별 볼트는 같은 데이터를 다른 질문으로 읽는 뷰이며 별도 진실 원본이 아니다.

Obsidian 그래프의 노드 이름은 Markdown 파일명이므로 파일명은 솔루션·종류·동작이 보이는 탐색용 표시 이름으로 만든다. 해시만 있는 파일명을 생성하지 않고, 이름 충돌 때만 짧은 해시를 뒤에 붙인다. 안정 ID는 JSON과 노트 내부에 유지해 검색·후속 화면의 결합 키로 사용한다.

Obsidian의 위키링크와 기본 그래프는 현재 볼트 안에서만 관계를 만든다. `obsidian://open?vault=<고유 볼트명>&file=<노트>`는 이미 등록한 다른 볼트로 이동시키는 링크다. 상위 볼트의 그래프 엣지는 교차 볼트 URI가 아니라 **상위 볼트 안의 대리 노트끼리 연결한 위키링크**로 만든다. 볼트별 `.obsidian/`은 사용자 설정이므로 기존 값을 덮어쓰지 않는다.

## 생성과 완료 검사

1. `capability_map.py validate`로 프로젝트·기능·관계의 근거를 검증한다. `render/check`는 과거 단일 `vault/` 출력의 호환 도구다. 새 멀티 볼트는 해당 프로젝트의 결정적 생성기와 `generation-manifest.json`을 둔다.
2. 생성기는 기존 소유 파일의 SHA-256을 확인한 뒤에만 갱신한다. 사용자 편집·수동 노트·기존 `.obsidian/`은 보존한다. `vaults/` 컨테이너를 Obsidian 볼트로 만들지 않는다.
3. `python3 <codegraph-skill>/scripts/check_multi_vault.py --version-dir <version>`을 실행한다. 이 검사는 데이터 입력 지문, 솔루션 볼트 누락, 볼트별 내부 링크·홈 도달성, 교차 볼트 URI, 생성 파일 지문을 확인한다. 이어서 대표 기능의 양쪽 코드와 계약·분기·결과를 사람이 읽어 검증한다.
4. 데이터와 볼트의 버전 차이를 `CHANGE_REPORT.md`에 수치와 의미로 적는다. 원본 데이터가 같고 볼트만 재배치됐다면 그것을 새 코드 분석으로 세지 않는다. 실제 Obsidian 앱에서 열어 보지 못했으면 화면 검증 미완료를 명시한다.
