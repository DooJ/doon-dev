# Development Orchestrator

이 스킬은 개발 실행 방식의 라우터이자 통합 책임자다. 하네스 회의나 장기 기억 승격을 기본 생성하지 않고, 이 문서의 자체 절차로 이번 개발 요청을 어떤 모드로 처리할지 정하고 끝까지 구현, 통합, 검증한다.

- 아래 모드 선택·통합·검증 절차를 기준으로 개발 요청을 끝까지 진행한다.
- Android/Kotlin, UI, 에러, 리뷰, 문서 갱신은 기존 도메인 스킬을 필요한 만큼만 연결한다.
- 페르소나는 말투 캐릭터가 아니라 판단 기준과 위험 감지 렌즈다.
- 단일 업무에서는 실제 서브에이전트를 소환하지 않는다. 메인 에이전트가 해당 전문 렌즈를 직접 적용한다.
- 디자인과 구현이 함께 필요한 화면 개선은 `design-build`로 다룬다.

## 모드 선택

| 모드 | 관계 | 선택 기준 | 처리 |
|---|---|---|---|
| `master-direct` | 사용자 ↔ 메인 에이전트 | 작고 일반적인 단일 구현, 변경 파일과 검증 경로가 분명함 | 메인 에이전트가 직접 구현하고 검증한다. |
| `specialist-direct` | 사용자 ↔ 메인 에이전트 | 앱, 프론트엔드, 백엔드 중 한 도메인이 분명하고 해당 위험 렌즈가 필요함 | 실제 위임 없이 메인 에이전트가 전문 렌즈로 직접 처리한다. |
| `design-build` | 사용자 ↔ 디자인-개발 오케스트레이터 | 기획 의도, UI/UX, 비주얼 개선, 실제 구현 가능성을 함께 다루는 화면 작업 | 디자인 델타를 먼저 정하고 프론트엔드/앱 렌즈로 구현한 뒤 시각 QA를 수행한다. |
| `orchestrated-parallel` | 사용자 ↔ 오케스트레이터 ↔ 실제 서브에이전트 | 앱+웹+백엔드처럼 둘 이상의 독립 작업면이 있고 계약, 통합, 병렬 검증이 필요함 | 작업 계약을 나누고 가능한 경우 실제 서브에이전트에게 위임한 뒤 통합 QA를 맡는다. |
| `review-assist` | 메인 에이전트 + 리뷰/QA 보조 | 구현은 직렬이지만 회귀 위험, 테스트 위험, acceptance criteria 누락 위험이 큼 | 메인 에이전트가 구현하고 독립 리뷰 또는 QA 렌즈로 검증을 추가한다. |

### 빠른 판정

- 파일 한두 개의 국소 변경이고 API, 데이터 모델, 화면 흐름 경계가 바뀌지 않으면 `master-direct`.
- 단일 Android/iOS, 웹 UI, API/DB 작업처럼 담당 도메인이 명확하면 `specialist-direct`.
- 사용자가 화면을 개선, 꾸미기, 다듬기, UX 수정, 시각 QA, 디자인 의도 반영과 실제 코드 반영을 함께 요구하면 `design-build`.
- 여러 코드베이스, 여러 런타임, API 계약과 UI 소비자, 모바일과 서버 변경이 동시에 있으면 `orchestrated-parallel`.
- 결제, 인증, 권한, 데이터 손실, 배포, 마이그레이션, 접근성, 회귀 위험이 크지만 구현 단위는 하나면 `review-assist`.
- 모드가 애매하면 더 작은 모드로 시작하고, 실제로 독립 병렬 작업면이 확인될 때만 확장한다.
- `master-direct` 판정이면 별도 오케스트레이션을 확장하지 않고 메인 에이전트가 읽기, 최소 수정, 관련 검증, 결과 보고를 한 번의 자체 완결 루프로 수행한다.

## 페르소나 렌즈

| 렌즈 | 중점 |
|---|---|
| `master-developer` | 기존 구조, 최소 변경, 통합 품질, 전체 검증 책임 |
| `ui-ux-designer` | 기획 의도, 사용자 행동, 정보 위계, 시각 밀도, 접근성, 구현 가능성 |
| `app-developer` | 앱 생명주기, 권한, 오프라인, 네트워크 흔들림, 모바일 UX |
| `frontend-developer` | 화면 상태, 반응형, 접근성, 컴포넌트 재사용, 브라우저 검증 |
| `backend-developer` | 데이터 모델, API 계약, 인증/권한, 트랜잭션, 실패 처리 |
| `qa-reviewer` | 재현성, 회귀 위험, acceptance criteria, 실제 실행 검증 |

단일 전문 작업에서는 "앱 쪽입니다. 제가 앱 개발자 렌즈로 바로 처리하겠습니다."처럼 보고하고 직접 실행한다. 실제 서브에이전트를 쓰지 않았다면 `서브에이전트`나 `병렬 팀`이라고 부르지 않는다.

## 실행 절차

1. 사용자의 목표와 성공 기준을 한 문장으로 정리한다.
2. 관련 파일, 모듈, 테스트, 실행 경로를 확인해 작업면을 나눈다.
3. 위 기준으로 모드를 선택하고, 복합 작업이면 공유 계약을 먼저 적는다.
4. `master-direct`와 `specialist-direct`에서는 메인 에이전트가 직접 읽기, 수정, 검증, 보고까지 수행한다.
5. `design-build`에서는 기획 의도와 현재 화면 근거를 잡고 구현 가능한 디자인 델타를 먼저 정한다.
6. `orchestrated-parallel`에서는 각 작업에 `scope`, `owner lens`, `inputs`, `outputs`, `done criteria`, `verification`을 붙인다.
7. 실제 서브에이전트 도구가 있고 병렬화 가치가 분명할 때만 위임한다. spawn/send/wait 같은 실제 증거가 없으면 `single-agent fallback`으로 보고한다.
   - 실제 위임은 현재 runtime과 사용자 지시가 허용한 범위에서만 한다. 사용 가능한 도구가 있다는 사실만으로 권한을 확대하지 않는다.
8. 서브에이전트 결과는 그대로 합치지 말고 API 계약, 타입, 상태 흐름, 오류 처리, 테스트 범위를 메인 에이전트가 재검토한다.
9. `review-assist`에서는 구현 후 diff, acceptance criteria, 위험 지점을 기준으로 QA 또는 리뷰 관점을 독립적으로 적용한다.
10. 각 변경 뒤 가장 좁은 관련 검증부터 실행하고, 최종적으로 acceptance criteria와 회귀 위험을 확인한다. 관련 검사 통과 뒤 새 변경·실패·미해결 위험이 없으면 반복 검증을 늘리지 않는다.
11. 최종 보고에는 선택 모드, 실제 위임 여부, 바뀐 파일, 검증 결과, 남은 리스크를 포함한다.

## Design Build 절차

`design-build`는 디자인 산출물만 만드는 모드가 아니다. 화면의 목적, 사용자의 다음 행동, 현재 구현 제약, 실제 코드 반영을 하나의 작업으로 묶는다.

1. 기획 의도, 대상 사용자 행동, 현재 화면의 문제, 유지해야 할 브랜드/컴포넌트 제약을 확인한다.
2. 새 방향 탐색이 필요하면 `ui-concept-director`, 기존 화면 개선이면 `design-generalist`, 반복 컴포넌트/토큰 기준이 필요하면 `design-system-curator`, 문구 개선이 핵심이면 `content-strategist`를 적용한다.
3. 디자인 델타를 구현 가능한 단위로 압축한다: layout, hierarchy, spacing, typography, color, component state, empty/loading/error/success, responsive, accessibility.
4. 프론트엔드 또는 앱 개발 렌즈로 기존 컴포넌트와 스타일 체계를 우선 확장해 구현한다.
5. 시각 QA는 실제 화면 근거로 확인한다. 가능한 경우 screenshot, browser/simulator 확인, 모바일/데스크톱 viewport, 긴 텍스트, 빈 데이터, 오류 상태를 본다.
6. 결과 보고에는 디자인 의도, 구현 변경, 검증 화면 또는 명령, 남은 시각/UX 리스크를 함께 적는다.

### 디자인 capability 해석

다른 플러그인의 스킬 이름은 설치 의존성이 아니라 선호 제공자다. 먼저 필요한 목적을 고르고, 현재 발견 가능한 제공자와 대체 경로를 결정한다.

| capability | 선호 제공자 | 제공자가 없을 때 |
|---|---|---|
| `design.concept-direction` | `ui-concept-director` | 사용자 목표와 제약을 근거로 2~3개 방향, 선택 기준, 보류 결정을 `inline_concept_brief`로 만든다. 새 브랜드 전략을 확정하지 않는다. |
| `design.screen-handoff` | `design-generalist` | layout, hierarchy, state, responsive, accessibility를 포함한 최소 `inline_screen_handoff`를 만든다. 시각 근거가 없으면 `partial`로 표시한다. |
| `design.system-governance` | `design-system-curator` | 기존 토큰·컴포넌트를 보존하는 범위만 구현한다. 새 토큰 체계나 거버넌스 확정은 `design_system_handoff`로 남긴다. |
| `content.ux-copy` | `content-strategist` | 기능 명확성·오류 복구·접근성에 필요한 최소 문구만 작성한다. 브랜드 보이스 재정의는 `content_handoff`로 남긴다. |

- 선호 제공자를 발견하면 해당 스킬의 계약을 적용한다.
- 같은 capability와 산출물 계약을 충족하는 다른 제공자가 있으면 대체할 수 있다. 단순히 이름이 비슷하다는 이유로 대체하지 않는다.
- 대체 경로를 사용하면 결과에 `provider_mode: preferred|equivalent|inline|handoff`와 적용 범위를 기록한다.
- capability가 현재 요청의 완료 조건이고 inline 계약으로도 충족하지 못하면 완료를 주장하지 않고 `partial` 또는 `blocked`로 보고한다.

## 스킬 사용 원칙

서브에이전트가 업무할 때 특정 스킬을 기계적으로 강제하지 않는다. 작업 계약과 사용자 요청을 기준으로 필요한 도메인 스킬이 자연스럽게 발동되게 한다.

- 메인 에이전트는 작업 범위상 필요한 스킬을 빠뜨리지 않을 책임이 있다.
- 서브에이전트에게는 좁은 목표와 산출물 기준을 주고, 필요한 경우에만 `design-generalist`, `frontend-developer lens`, `kotlin-basics`처럼 적용해야 할 기준을 명시한다.
- Android/Kotlin, 디자인 시스템, 에러 대응, 코드 리뷰처럼 프로젝트 규칙상 특정 스킬이 필요한 경우에는 worker 계약에 해당 기준을 포함한다.
- "이 스킬을 반드시 써서 개발해"가 기본값은 아니다. 기본값은 현재 업무에 맞는 규칙과 스킬을 필요한 만큼만 적용하는 것이다.

## 병렬 위임 계약

실제 서브에이전트를 사용할 때는 각 worker에게 아래만 전달한다.

- 이번 작업의 좁은 목표
- 읽어야 할 파일 또는 조사 범위
- 수정 허용 범위
- 산출물 형식
- done criteria와 검증 명령
- 다른 worker와 공유해야 하는 계약
- 재개가 필요한 경우 현재 기준·완료·남은 일·실행 중 도구 식별자를 전달한다.
- 적용해야 할 도메인 기준이나 관련 스킬. 필요한 경우에만 명시한다.

숨은 추론, 전체 raw history, 무관한 프로젝트 기억, 비밀 값은 전달하지 않는다. worker 결과가 충돌하면 오케스트레이터가 선택지와 영향 범위를 정리하고, 사용자 가치 판단이 필요한 경우 사용자에게 묻는다.

## 보고 문구

- 단일 직접 처리: `mode: master-direct`
- 단일 전문 처리: `mode: specialist-direct(app-developer)`, `실제 서브에이전트 없이 메인 에이전트가 앱 렌즈로 직접 처리`
- 디자인-개발 화면 개선: `mode: design-build`, `디자인 의도와 구현 가능성을 함께 정리한 뒤 실제 화면에 반영`
- 병렬 위임 성공: `mode: orchestrated-parallel`, `frontend/backend worker를 실제 위임했고 메인 에이전트가 계약과 통합 QA를 담당`
- 병렬 fallback: `mode: orchestrated-parallel -> single-agent fallback`, `실제 위임 증거가 없어 메인 에이전트가 작업면을 순차 처리`
- 리뷰 보조: `mode: review-assist`, `구현 후 QA/review 렌즈로 회귀 위험을 재검토`

## 금지 사항

- 작은 단일 업무에 실제 서브에이전트를 소환하지 않는다.
- 실제 위임 증거 없이 `actual subagent`, `병렬 처리 완료`, `팀 검토 완료`라고 말하지 않는다.
- 페르소나 렌즈를 근거로 기존 코드 구조, 테스트 결과, 사용자 명시 지시를 덮어쓰지 않는다.
- Huggies 라우팅 조건(사용자 명시 또는 장기 상태·회의·gate·handoff)이 없으면 project/meeting/company memory 산출물을 만들지 않는다.
- `design-build`에서 예쁜 시안만 만들고 실제 구현 가능성, 상태, 반응형, 접근성 검증을 건너뛰지 않는다.
- 구현 검증 없이 완료를 선언하지 않는다.
