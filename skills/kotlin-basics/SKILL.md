# 핵심 기본 규칙 (Core Global Rules)

## 코틀린 일반 가이드라인
기본 원칙과 명명 규칙을 준수하여 코드를 작성하고, 수정 및 리팩토링을 수행하세요.

## 적용 방식
- 먼저 기존 모듈의 Kotlin 버전, Android/서버 여부, lint/formatter 설정, 주변 파일 스타일을 확인하세요.
- 아래 규칙은 새 코드와 수정 코드에 우선 적용하되, 기존 코드와 충돌할 때는 변경 범위를 좁혀 일관성을 해치지 않게 조정하세요.
- 동작 변경이 필요한 리팩토링과 순수 스타일 정리는 구분해서 설명하세요.
- 사용자의 요청과 직접 연결되지 않는 리팩토링, 추상화, 옵션 추가는 하지 않습니다. 모든 변경 라인은 버그 수정, 요구사항 구현, 검증 보강 중 하나로 설명 가능해야 합니다.

## 기본 원칙
- 변수명, 함수명 등의 코드는 영어를 사용하되, 설명 주석과 문서는 한국어로 작성하세요.
- 타입 표기는 프로젝트의 lint/formatter와 공개 API 경계를 우선합니다. 공개 API, 직렬화/DB 경계, 추론이 모호한 식, 의도를 숨기는 복합 타입에는 명시하고, 자명한 local 변수와 람다는 Kotlin의 타입 추론을 허용합니다.
  - `Any`나 과도하게 넓은 타입으로 도메인 의미를 숨기지 마세요.
  - 별도 타입은 경계 보호나 불가능한 상태 제거에 실제 이득이 있을 때 만드세요.
- 일반적인 클래스 참조는 프로젝트의 import 관례를 따릅니다. 이름 충돌을 풀거나 생성 코드·공개 API 경계를 명확히 해야 할 때는 전체 클래스명 사용도 허용합니다.
- 함수 내부에 의미 없는 빈 줄을 남기지 마세요.

## 명명 규칙
- 클래스명은 PascalCase를 따르고 파일명은 선언 종류와 프로젝트 관례에 맞춥니다.
- 변수, 함수, 메서드명에는 카멜 표기법(camelCase)을 사용하세요.
- 패키지·디렉터리명은 기존 모듈과 Kotlin/Android 도구의 관례를 따르세요. 일괄 이름 변경은 요청 범위에 포함될 때만 합니다.
- 환경 변수에는 대문자(UPPERCASE)를 사용하세요.
- 동작을 수행하는 함수는 의도가 드러나는 동사를 우선하되, getter·팩터리·DSL·테스트 이름은 해당 프로젝트 관례를 따르세요.
- 불리언(Boolean) 변수에는 동사(`isX`, `hasX`, `canX`)를 사용하세요.

## 함수/메서드 지침
- 단일 목적을 가진 매우 간결하고 명확한 함수를 작성하세요.
- 예외 상황이나 실패 조건에 대한 빠른 조건 검사 및 반환(Early checks and returns)을 통해 블록 중첩(Nesting)을 최소화하세요.
- 고차 함수(map, filter, reduce 등)를 적극 사용하여 가독성을 높이세요.
- 기본값은 인수 생략이 실제로 유효할 때만 사용하세요. nullable 값과 외부 입력은 의미에 맞게 검사하며, Kotlin에 `Undefined` 값이 있다고 가정하지 않습니다.
- 관련 매개변수가 반복되거나 불변식을 함께 지켜야 할 때만 객체로 묶으세요.
- `when`은 sealed class, enum, 상태 모델처럼 닫힌 분기에서 exhaustiveness가 드러나도록 사용하세요.
- side effect가 있는 로직은 `map`, `also`, `apply` 안에 숨기지 말고 명시적인 함수나 블록으로 분리하세요.

## 데이터 설계
- 데이터 모델링에는 데이터 클래스(`data class`)를 중점적으로 활용하세요.
- 원시 타입(Primitive types) 남용을 피하고, 관련된 항목은 복합 타입(Composite types)으로 캡슐화하세요.
- 데이터의 불변성(Immutability)을 지향하세요. (val 변수 사용, 읽기 전용 컬렉션 권장)
- 외부 API, DB, UI 상태처럼 경계가 다른 모델은 필요하면 별도 타입으로 분리하고 mapper를 둡니다.
- nullable 값은 도메인상 실제로 결측이 가능한 경우에만 허용하고, 호출부에서 의미 없는 `!!` 사용은 피하세요.

## 코루틴과 비동기
- suspend 함수는 호출자가 취소할 수 있어야 하며, 불필요하게 `GlobalScope`를 사용하지 마세요.
- I/O, CPU 작업, UI 업데이트의 dispatcher 경계를 명확히 분리하세요.
- `Flow`는 수집 위치의 생명주기와 backpressure, 중복 수집 가능성을 함께 고려하세요.

## 예외 처리
- 처리 불가능한 예상치 못한 상황에서만 예외(Exceptions)를 발생시키고 잡으세요. (제어 흐름 용도로 예외 사용 금지)
- 잡은 예외는 반드시 적절히 로깅하거나 리커버리 로직을 실행하여 복구 컨텍스트를 제공하세요.
- 실패가 정상적인 도메인 흐름이라면 `Result`, sealed result, 명시적 상태 모델을 우선 고려하세요.

## 완료 기준
- 변경한 코드가 null-safety, import, 프로젝트 lint의 타입 표기, 네이밍 규칙을 만족하는지 확인하세요.
- 새 로직이 가장 단순한 형태인지, 기존 함수/타입으로 충분한데 새 구조를 만든 것은 아닌지 점검하세요.
- 테스트가 있다면 관련 테스트를 실행하고, 실행하지 못했다면 이유와 남은 위험을 명시하세요.
