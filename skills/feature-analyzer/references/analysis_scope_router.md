# 분석 범위 라우터
코드 분석 요청은 먼저 기능 단위 역기획인지 프로젝트 전체 역기획인지 분류한다.

## 범위 분류
| 범위 | 사용자 표현 | 분석 초점 | 후속 문서화 |
|---|---|---|---|
| 기능 역기획 | 이 기능, 이 화면, 이 API, 이 플로우, 이 로직 | 특정 진입점부터 결과까지의 동작 | 해당 기능의 요구사항, 화면, API, QA 섹션 갱신 |
| 프로젝트 전체 역기획 | 이 프로젝트 분석, 전체 구조 정리, 코드 기반 문서화, 전체 기능 파악 | 도메인, 화면/API, 데이터, 아키텍처, 운영/테스트 단서 | 프로젝트 개요, 코드 맵, 기능 카탈로그, 기술/데이터/QA 문서 갱신 |
| 온보딩 구조 분석 | 처음 보는 사람이 이해하게, 인수인계, 코드 맵 | 읽는 순서, 주요 모듈, 실행/검증, 위험 지점 | `docs/onboarding/*` 갱신 |
| 문서화용 명세 추출 | 명세서로 뽑아줘, 문서화해줘, 리빙독 반영 | 코드 사실을 문서 단위로 정리 | `living-doc-writer` 입력으로 전달 |

## 판별 규칙
1. 대상 이름이 기능, 화면, API, 모듈, 파일로 좁혀져 있으면 기능 역기획이다.
2. 대상이 프로젝트명, 저장소, 앱 전체, 서비스 전체면 프로젝트 전체 역기획이다.
3. 사용자가 "문서화", "정리", "리빙독"을 함께 말하면 분석 결과를 문서 갱신 후보로 정리한다.
4. 범위가 애매하면 먼저 전체 구조를 얕게 훑고, 기능 후보 목록과 추천 분석 범위를 제시한다.

## 기능 역기획 최소 산출물
- 기능 목적
- 진입점과 트리거
- 정상 흐름
- 실패/예외 흐름
- 상태 전이
- 데이터 저장소와 외부 연동
- 권한, 네트워크, 캐시, 동시성 조건
- 관련 파일과 함수 근거
- 리빙독 갱신 후보

## 프로젝트 전체 역기획 최소 산출물
- 프로젝트 한 줄 정의
- 주요 도메인/기능군 목록
- 화면, API, 배치, 서비스 진입점 지도
- 데이터 모델과 저장소 단서
- 외부 연동과 설정
- 아키텍처 레이어와 모듈 책임
- 테스트, 빌드, 배포, 운영 단서
- 문서 누락과 오래된 문서 후보
- 리빙독 생성/갱신 후보

## 질문 예시
```markdown
분석 범위가 두 가지로 갈립니다.

- 기능 역기획: 특정 화면/API/플로우를 깊게 분석
- 프로젝트 전체 역기획: 전체 도메인, 구조, 데이터, 운영 단서를 훑고 리빙독 후보를 정리

현재 표현만 보면 프로젝트 전체 역기획이 맞아 보입니다. 이 범위로 진행하겠습니다.
```
