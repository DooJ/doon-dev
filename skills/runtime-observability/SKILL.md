# 런타임 관측 설계

## 범위

관측할 사용자 실패와 운영 질문을 먼저 정한다. 서비스 간 요청, 비동기 작업, 외부 호출처럼 원인 연결이 어려운 경로에서 필요한 신호만 추가한다. Sentry가 이미 있으면 중복 수집 대신 `sentry-observability`의 기존 release·event 계약을 확인한다.

## 계측

1. 현재 로그·지표·trace와 누락된 질문을 확인한다. 무엇을 알기 위해 새 신호가 필요한지 설명할 수 있어야 한다.
2. 구조화된 오류·상태 정보, 지연·실패율 같은 지표, 경로를 잇는 상관 ID를 필요한 곳에만 둔다. 성공·실패와 재시도·부분 실패를 구분한다.
3. 토큰, 요청 본문, 개인정보를 기본 수집하지 않는다. 표본율, 보존 기간, 접근 권한과 외부 전송 여부를 확인한다. 외부 관측 서비스 연결은 별도 승인 범위를 따른다.
4. 통제된 정상·실패 사례로 신호가 실제 수집되고 서로 연결되는지 확인한다. 대시보드나 알림은 운영 판단에 필요한 경우에만 추가한다.

제품 행동 분석과 사업 지표 수집은 별도 목적·동의·지표 정의가 필요하다. 이 스킬은 운영 장애를 이해하기 위한 계측에 한정한다.

## 결과

관측 질문, 사용한 신호와 저장 위치, 개인정보 경계, 검증한 사례와 남은 공백을 보고한다.
