# 인터페이스 계약 설계

## 적용

- 먼저 실제 제공자와 소비자, 현재 호출 경로와 기존 계약을 확인한다. 공개 범위가 작으면 별도 설계 문서 없이 변경 지점에서 계약을 명시한다.
- 요구사항의 사용자 동작과 기술 계약을 구분한다. 기존 프로젝트의 API 규약, 타입·스키마, 인증·권한, 오류 형식을 우선한다.

## 계약 결정

1. 소비자가 기대하는 입력, 출력, 상태 전이와 불변 조건을 적는다. 필수·선택 필드, 빈 값, 경계값과 잘못된 입력을 구분한다.
2. 성공뿐 아니라 오류 코드·예외·부분 실패·타임아웃의 의미를 정한다. 재시도 가능한 작업이면 중복 요청과 멱등성을 확인한다.
3. 기존 소비자에 미칠 영향을 확인한다. 호환 변경인지, 소비자 수정이나 단계적 전환이 필요한 변경인지 밝힌다.
4. 대표 소비자와 실패 경로를 실제 호출 또는 계약 테스트로 확인한다. 구현이 계약과 달라지면 문서보다 구현과 소비자 검증을 먼저 바로잡는다.

여러 런타임의 통합 작업이면 `development-orchestrator`에 이 계약을 전달한다. 기존 인터페이스의 제거까지 포함하면 `deprecation-migration`으로 전환 단계를 정한다. 기술 문서는 실제 확정된 계약만 프로젝트 원본 위치에 갱신한다.

## 결과

변경한 경계, 영향받는 소비자, 호환성·오류 처리 결정, 실행한 검증과 남은 미확인 소비자를 짧게 보고한다.
