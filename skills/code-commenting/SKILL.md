# 문서화 및 주석 (Comments) 규칙


## 핵심 정책 (Core Policy)
- 프로젝트가 한국어 주석을 사용하는 경우 새 주석과 문서화 블록도 한국어로 명확하게 작성합니다. 기존 저장소의 언어 규칙이 다르면 해당 규칙을 우선합니다.
- 주석은 코드가 이미 말하는 사실을 반복하지 말고, 배경, 제약, 선택 이유, 실패 조건, 도메인 규칙을 보완해야 합니다.
- 주석이 필요한지 애매하면 먼저 이름, 타입, 함수 분리로 설명 가능성을 높이고, 그래도 남는 맥락만 주석으로 남깁니다.
- 요청받지 않은 주석 대량 정리나 문체 통일은 하지 말고, 변경한 코드와 불일치하거나 호출자가 알아야 할 계약을 설명하는 주석만 갱신합니다.

## 작성 대상별 지침

### 1. 클래스 (Class)
- 공개 API, 핵심 도메인 경계, 이름과 타입만으로 의도가 충분히 드러나지 않는 클래스나 인터페이스에만 KDoc을 작성합니다.
- 외부에서 재사용되는 타입은 호출자가 알아야 하는 책임 범위, 생명주기, 스레드/호출 제약, 주요 협력 객체만 짧게 포함합니다.

### 2. 함수 및 파라미터 (Function & Parameter)
- 시스템의 핵심 코어 로직이 수행되는 함수나 특별한 비즈니스 룰이 반영되어 동작 의도를 별도 전달해야 하는 함수에는 KDoc으로 상세 설명 및 주의사항을 기재합니다.
- 복잡한 동작을 가진 함수나 클래스의 매개변수(특히 이해가 모호할 수 있는 제어 플래그 속성, Nullable 매개변수 등)에는 `@param` 태그를 활용해 구체적인 안내를 덧붙이세요.
- 반환값이 상태, 실패, 부분 성공, side effect를 포함한다면 `@return` 또는 본문 설명으로 호출자가 알아야 할 계약을 명시하세요.
- 예외를 던지는 함수는 예외가 발생하는 조건과 호출자가 취해야 할 대응을 간결히 남기세요.

### 3. 본문 인라인 주석 (Inline Comments)
- 단순히 코드가 무엇을 하는지 번역하는 무의미한 설명(`// 카운트 증가`, `// 객체 생성` 등)은 제거하고 지양하세요.
- 대신 이 코드가 **무엇을 위해 쓰였는지, 왜 이런 형태의 로직을 선택했는지(Why, Intent)**를 알리는 데 집중하세요.
- 임시 우회, 성능상 트레이드오프, OS/API 버전별 제약, 외부 시스템 버그 대응은 주석으로 근거를 남기세요.

## [필수주의] 코드와 주석의 동기화 (Code-Comment Sync)
- **절대 죽은 주석을 방치하지 마세요.**
- 시스템 리팩토링이나 기능 추가 등으로 인해 함수의 본문 로직이나 의도가 변경되었을 경우, 이에 맞춰 클래스 주석이나 관련된 KDoc, 인라인 주석도 **반드시 함께 갱신(Update)**해야 합니다.
- 수정되지 않고 남겨져 현재 사실과 다른 주석은 심각한 기술 부채를 야기합니다.

## 완료 전 점검
- 새로 추가한 주석이 현재 코드와 실제 동작을 정확히 설명하는지 확인하세요.
- 삭제된 로직, 이전 정책, 더 이상 쓰지 않는 TODO가 남아 있지 않은지 확인하세요.
- 공개 API의 KDoc은 호출자가 알아야 하는 입력, 출력, 실패 조건을 포함하는지 점검하세요.
